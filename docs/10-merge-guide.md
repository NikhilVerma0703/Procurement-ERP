## 4. Cut-over: the exact steps

Where each command runs:
- **This repository** (`C:\Users\User\Desktop\Procurement ERP`): the backup is in `data/erpnext-backup` (gitignored).
  Its `.env` is the local database, so every command here that reaches Neon gets `DATABASE_URL` set in the shell
  for that window. The shell's value wins over `.env`.
  - PowerShell: `$env:DATABASE_URL = "<the direct URL>"`
  - Git Bash: `export DATABASE_URL="<the direct URL>"`
- **The Main ERP checkout:** its `.env` is production by convention.

Use the **direct** connection string from Neon (host without `-pooler`) for every script: the import is one long
transaction.

### 4.1 Rehearsal, on a copy of production (days before)

1. **A copy.** Neon › the ERP's project › Branches › create a branch of `main` (e.g. `purchase-rehearsal`). Copy its
   direct connection string. Production is not touched.
2. **The schema**, from this repository, with `DATABASE_URL` = the branch:
   `npx prisma db execute --schema prisma/schema.prisma --file merge/purchase-module.sql`.
   Then run the script's `CHECK (after)` queries in Neon's SQL editor (one `PURCHASE` row; 9 types, 49 tables,
   701 columns, 73 indexes, 84 foreign keys; one `action_log` row).
3. **The data:** `npm run import:erpnext -- --target <the branch's host>`. It prints `Database: <host>/<db>` first.
   It must end with "✓ Import matches the backup."
4. **The proof**, all read-only:
   - `npm run verify:erpnext`: "✓ The database holds exactly what the backup has." It compares every count, money
     total and relation, and the stored files byte for byte.
   - `npm run golden`: 0 unexplained differences.
   - `npx tsx --conditions=react-server scripts/check-sheets.ts`: every sheet matches.
5. **The screens:** a Vercel preview of the merge branch, with its database variables (Preview, that git branch
   only) on the Neon branch. The Procurement Manager works through [11-acceptance.md](11-acceptance.md) there.
6. Delete the Neon branch.

### 4.2 Cut-over day (production)

1. **Stop entering POs on the old site** from an agreed time.
2. **The final backup** (owner-approved, as on 19-11-2026). On the old site:
   - Open `/app/backups` › ⋯ › **Download Files Backup** ("Queued for backup"). After 2–3 minutes, reload.
   - If the list stays empty, the browser is showing its saved copy of the page: clear `_page:backups` (or Frappe's
     Reload) and open it again.
   - Download the new `…-database.sql.gz`, and the two archives at `/backups/<same name>-files.tar` and
     `-private-files.tar`, into this repository's `data/erpnext-backup`. The importer takes the newest set.
3. **A way back:** Neon › create a branch of production now (e.g. `before-purchase-<date>`). It is instant, and it is
   the restore point.
4. **The schema** (Main ERP checkout; its `.env` is production):
   `npx prisma db execute --schema prisma/schema.prisma --file scripts/NNNN-purchase-module.sql`, then its CHECK
   queries. It only adds things: the `PURCHASE` value and the `purchase_*` tables. Running it again changes nothing.
5. **The data**, once (this repository, `DATABASE_URL` = production's direct URL in the shell):
   `npm run import:erpnext -- --target <production host>` → "✓ Import matches the backup" with the final backup's
   counts (3,227 POs and the Stock documents on the 21-11-2026 backup).
6. **The proof:** `npm run verify:erpnext`, `npm run golden` and `check-sheets.ts`, as in 4.1. Keep the reports from
   `data/reports/`.
7. **Deploy:** merge the module's PR into `main`. Vercel builds it with `prisma generate && next build`; no step of
   the build touches the database.
8. **Logins:** in Users & Roles, give the buyers `PURCHASE` (and approval, by decision 1).
9. **On the live site:**
   - `/purchase/orders` reads "20 of 3,227" (or the final backup's count).
   - Open, print and export a few POs, and the acceptance checklist's section I.
   - `npm run verify:erpnext` once more: still ✓, since nothing has been done there yet.
10. **Hand over.** Switch the old site off, or leave it read-only until its subscription ends.

### 4.3 After go-live

- **The importer is not run again.** It refuses on its own once anything was done in the module (§6). `--force`
  would undo the team's work; use it only on the owner's say-so, and never after go-live.
- **Every later deploy is code only.** A module schema change is a new numbered, additive script plus the model
  change in `schema.prisma`. Never `prisma db push` or `migrate reset` on production; the Main ERP's `db:push` and
  `db:migrate` refuse a database that is not local.
- **Backups** are Neon's history (point-in-time restore), as for the rest of the ERP.

### 4.4 If something is wrong

- **The import failed:** it is one transaction, so nothing was loaded. Fix the cause and run it again.
- **The reconciliation shows differences:** read `data/reports/import-….md`. While nothing has been done in the
  module, `--force --target <host>` reloads.
- **Back out entirely:**
  1. Roll the deploy back (Vercel › Deployments › promote the previous one).
  2. Run the script's UNDO section by hand. It drops the `purchase_*` tables. The `PURCHASE` value can stay.
  3. Restoring the step-3 branch is the other way back, right after the cut-over only: it also rolls back the rest
     of the ERP.

## 5. Decisions the merge needs

1. **Who approves.**
   - The old workflow: "Purchase Head" raised a PO, "Admin" approved it.
   - In practice, over the last 12 months both buyers (Thiru R, Althaf) held both roles. They raised 1,629 POs and approved 1,441 between them.
   - Options:
     - **a.** `PURCHASE` may also approve, as practised.
     - **b.** Approval stays with the ERP's `ADMIN`.
     - **c.** A second role, `PURCHASE_APPROVER`.
2. **Attachment size.** Applied 19-11-2026 with the recommended default: 4,000,000 bytes, as the Lab module, because
   Vercel refuses a request near 4.5 MB. The old site allowed 10 MB; the 5 files on old POs are 344 KB at most.
3. **Which mailbox sends PO emails.** The writer's own SMTP settings, else the ERP's global ones (the Main ERP's rule, as recommended); or one purchase mailbox for everyone.
4. **The three notifications** stay off (the old site last sent one on 21-09-2024) unless you switch them on.

## 6. Keeping production data safe

| Risk | What stops it |
|---|---|
| A deploy resets or changes the database | Vercel runs `prisma generate && next build` only: no migrate, no push. Every module page is dynamic, so the build reads no data. |
| `prisma db push` or `migrate` run on production | The Main ERP's `db:push` and `db:migrate` refuse a database that is not on the machine (`scripts/require-local-database.ts`); this repository's `db:migrate` does the same (19-11-2026). |
| The schema script run twice | Every statement is "if not exists"; a second run adds and logs nothing (checked). It never drops or alters an existing table. |
| The importer pointed at the wrong database | It prints `host/database` first. It writes to a database on another machine only when `--target` names exactly that host (`lib/purchase/migrate/target.ts`, after the Main ERP's `localDatabase.ts`). |
| The importer run again over live work | It refuses when anything changed since the last import (`lib/purchase/migrate/load.ts`): a row added or removed in any module table (a PO, a comment, a like, an upload, a deleted draft), a PO or master saved after it, or any record made here. Only `--force` passes, and it is one transaction: a failure leaves the database as it was. |
| Data that depends on this PC | Nothing at runtime reads a local file. Attachments and the logo are in `purchase_files`; the fonts come with pdfmake; the print layouts are code. `data/` is only the importer's input. |
| Losing data later | Neon's point-in-time history, as for every other module. |

**Proof at any time before the team starts work:** `npm run verify:erpnext` (read-only). After that the counts
move on, as they should; `npm run golden` still recomputes every PO against its stored figures.

## 7. Vercel's limits, and how the module fits them

Measured 19-11-2026 on a production build (`next build`, then `next start`) with the 3,217 POs.

| Limit | How the module fits |
|---|---|
| Function time (the Main ERP sets 60 s at most) | `maxDuration = 60` on every module page and the actions it runs (`src/app/purchase/layout.tsx`), and on the export and print routes; 30 s on uploads, as Lab. Bulk Approve, Reject and Delete go in turns of 20 records a request, with a count on the button ("40 of 120"). |
| Request body, about 4.5 MB | Uploads of at most 4,000,000 bytes, checked in the dialog and the route (`orders/attachment-limit.ts`). |
| Response body, about 4.5 MB (not streamed) | One print file holds at most 40 sheets: a sheet is 70 KB on average and 93 KB at most, so 40 is at most 3.7 MB. A file over 4.2 MB is refused. The Excel export of all 3,217 POs is 0.85 MB (1 s); one PO sheet is about 66 KB (0.2 s). |
| Page size | Pages are streamed by Next. A list of 500 POs is about 1.9 MB; the old site's largest page, 2,500, is about 8.9 MB and slow on a phone. |
| Database connections | The app uses the ERP's pooled URL; scripts use the direct one (§4). |
| Time zone (Vercel runs in UTC) | Every date uses the site's fixed India offset, so the server's clock changes nothing. |
